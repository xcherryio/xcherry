# Pull Workers

Use a pull Worker when the application can reach Dex Server but cannot accept inbound WorkerService calls. Configure the Worker's pull options and advertise a pull WorkerTarget through the Client default or a StartFlow or SubFlow FlowConfig override. A pull target has no address and cannot be headless. Keep listening Worker targets for applications that accept inbound calls. See the published [Pull Workers guide](https://docs.superdurable.io/production/pull-workers).

Copy application setup from the runnable [Go](https://github.com/superdurable/dex/blob/sdk-go/v1.14.1/examples/go/production/pull-workers/worker.go), [Java](https://github.com/superdurable/dex/blob/sdk-java/v1.14.1/examples/java/src/main/java/io/superdurable/dex/production/pullworkers/PullGreetingExample.java), [Python](https://github.com/superdurable/dex/blob/sdk-python/v1.14.1/examples/python/dex_examples/production/pull_workers.py), [TypeScript](https://github.com/superdurable/dex/blob/sdk-typescript/v1.14.1/examples/typescript/src/production/pull-workers.ts), or [Rust](https://github.com/superdurable/dex/blob/sdk-rust/v1.14.1/examples/rust/src/production/pull_workers.rs) example at each language's published SDK tag. These examples include bounded registration waits, cleanup on startup failure, and snapshot-based readiness helpers. Combine those helpers with application lifecycle health for production probes.

Each pull Worker opens outbound streams to its app Worker ID queue and every Flow type it registers. Flow types must be unique within a Dex Server. The app Worker ID identifies one process, changes after every restart, and cannot equal a registered Flow type. Let the SDK generate it unless a deployment needs an explicit process-unique value. Dex first tries the previously used app Worker ID. When that ID has no connected streams after a restart, crash, or deployment, Dex immediately tries the Flow type queue; the sticky wait applies only while that ID still has connected streams. Keep durable state in Dex; sticky routing does not promise the same process.

If no Worker accepts a task within the dispatch wait, a Step gets a retryable unavailable failure that **consumes one Step retry**. An RPC caller gets an Unavailable error. Pull delivery is at least once: a disconnected Worker can receive the same call again if Dex has not received output. Make external effects idempotent and reconcile uncertain outcomes. For a pull target, the local phase of **ASYNC** durability is one attempt; later attempts receive the last recorded heartbeat.

With Server v1.12.0 and a v1.12.0 pull Worker SDK, a Worker that does not register the requested Step type or RPC name declines it before application code runs. Dex excludes that Worker and tries another Worker without consuming a Step attempt. The regular dispatch wait is 10 seconds, including RPCs; the local Step dispatch wait is 3 seconds. If no capable Worker accepts within that wait, the Step receives a named failure and follows its failure and retry policy. The RPC caller receives **FailedPrecondition** naming the RPC, matching the legacy not-registered status code. Older Servers or SDKs retain the prior not-registered Worker error. During a rolling deployment, start Workers that add names before stopping old Workers; keep changed Step logic compatible because old Workers still serve the names they register.

## Startup registration and readiness

Go SDK v1.13.0 and Java, Python, TypeScript, and Rust SDK v1.14.0 expose startup registration waits and readiness snapshots:

| SDK | Startup wait | Readiness probe | Opt-in rejection shutdown |
| --- | --- | --- | --- |
| Go | **Worker.WaitPullRegistered(ctx)** | **Worker.PullRegistrationState().IsReady** | **PullWorkerOptions.StopOnPermanentStreamRejection** |
| Java | **Worker.waitPullRegistered(Duration)** | **Worker.getPullRegistrationState().isReady()** | **PullWorkerOptions.Builder.stopOnPermanentStreamRejection(true)** |
| Python | **Worker.wait_pull_registered(timeout=30)**; await on **AsyncWorker** | **worker.pull_registration_state().is_ready** | **PullWorkerOptions(stop_on_permanent_stream_rejection=True)** |
| TypeScript | **worker.waitPullRegistered({ timeoutMs: 10_000 })** | **worker.pullRegistrationState().isReady** | **pull.stopOnPermanentStreamRejection: true** |
| Rust | await **worker.wait_pull_registered()** | **worker.pull_registration_state().is_ready** | **PullWorkerOptions::stop_on_permanent_stream_rejection(true)** |

Start the blocking Go, Java, Python, or Rust Worker on another goroutine or thread; start Python's AsyncWorker in another task. TypeScript **start()** returns after local startup, so await it before the registration wait, or supervise **run()** separately. Use a bounded startup wait until the app Worker ID queue and every registered Flow type queue have each registered at least once. Concurrent waits before or after startup are safe. Startup failures wake waiters. Cancellation or timeout ends only that wait; it does not stop the Worker. Stop before initial registration and listening mode return errors. Once registration succeeds, later waits succeed, even after Stop; the wait proves registration, not free handler capacity.

Use the readiness snapshot for later probes. After initial registration, transient disconnects and ownership moves do not flap readiness. A permanent rejection makes it false only when that queue has no other registered stream. Queue entries expose the queue name, whether a registered stream exists, and the last permanent error using each language's native names. Successful re-registration clears that queue's error. Stop alone does not clear latched readiness: combine the snapshot with application lifecycle health and remove a stopping Worker from service separately.

Before initial readiness, a permanent rejection on a queue with no other registered stream fails the wait with **PullRegistrationError**. Rust returns an **SdkError** whose **pull_registration_error()** accessor exposes that typed rejection. The rejection identifies the queue and preserves the original transport error. Permanent statuses are **Unauthenticated**, **PermissionDenied**, **InvalidArgument**, **Unimplemented**, and **ResourceExhausted**. By default the Worker keeps retrying rejected streams with a one-minute delay. A rejected surplus stream records the last permanent error and retries while another registered stream keeps the queue ready; matching limits during rolling overlap must not cause a serving Worker to exit.

The opt-in rejection shutdown defaults to false in every SDK. When true, the first permanent rejection leaving its queue with no registered stream makes the Worker drain all queues within its configured stop drain timeout, request cancellation after that deadline, wait for handlers, and report the rejection. Handlers must respond to cancellation; the deadline does not force an unresponsive handler to return. Go, Java, Python, and Rust report it from **Start** or **start()**. TypeScript reports it from **run()**; **start()** retains its non-blocking startup contract. Rust preserves the typed rejection through **pull_registration_error()**. Always call **Stop**, **stop()**, or TypeScript **close()** before process exit; cleanup remains safe after the blocking run returns.

For rolling deployments, start replacement Workers and wait for their registration before stopping old Workers. Keep handling blocking Worker run failures after startup. See each language's startup and error-handling details: [Go](../go/go.md), [Java](../java/java.md#pull-workers-and-dex-credentials), [Python](../python/python.md#pull-workers-and-dex-credentials), [TypeScript](../typescript/typescript.md#pull-workers-and-dex-credentials), and [Rust](../rust/rust.md#pull-workers-and-dex-credentials).

## Heartbeats, capacity, and shutdown

Server v1.10.1 enforces the configured **HeartbeatTimeout** for pull Steps, as for listening Workers. Earlier Server v1.10.0 does not enforce it in pull mode. Cancellation reaches a Step handler through heartbeats. A long-running handler that must observe cancellation should record heartbeats within its **HeartbeatTimeout** and handle the resulting cancellation promptly. Set the timeout to tolerate healthy quiet periods while bounding a lost Worker, and keep each attempt within its method timeout.

The maximum concurrent task count caps active handlers. Idle streams per queue keep work ready, and each stream handles one task at a time. With SDK v1.14.1 in all five languages, a Worker gracefully closes surplus idle streams after tasks finish, preserving readiness and the configured registered idle streams per queue. After load drops, the steady-state bound per Worker is **M + (F + 1) × I**, where **M** is maximum concurrent tasks, **F** is registered Flow types, and **I** is idle streams per queue. The extra queue is the app Worker ID queue. Transient peaks during a burst remain bounded by **matching.maxConcurrentTasksCap** per app Worker ID on each matching owner and **matching.maxStreams** per Matching instance. Size for both caps, not only the steady-state bound. Busy streams receive no idle Ping, so record task heartbeats often enough to keep load-balancer connections active. See [Server deployment](operations.md#pull-worker-server-setup).

On Stop, the Worker stops accepting assignments and waits for handlers up to its drain timeout (30 seconds by default). It then requests cancellation and waits for handlers to return. A half-closed task stream, including one awaiting a server-directed reconnect, is bounded by the remaining drain deadline. Keep handlers responsive to cancellation and allow shutdown to complete before terminating the process.

For scale to zero, configure [worker.wake](operations.md#worker-wake-hook). Dex sends a best-effort wake notification after the sticky wait and continues the same dispatch attempt. Size dispatch waits, Worker startup time, and Step retry policy together; the notification does not guarantee a Worker starts in time.
