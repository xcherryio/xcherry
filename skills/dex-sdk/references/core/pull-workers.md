# Pull Workers

Use a pull Worker when the application can reach Dex Server but cannot accept inbound WorkerService calls. Configure the Worker's pull options and advertise a pull WorkerTarget through the Client default or a StartFlow or SubFlow FlowConfig override. A pull target has no address and cannot be headless. Keep listening Worker targets for applications that accept inbound calls. See the published [Pull Workers guide](https://docs.superdurable.io/production/pull-workers).

Copy application setup from the runnable [Go](https://github.com/superdurable/dex/blob/sdk-go/v1.13.0/examples/go/production/pull-workers/worker.go), [Java](https://github.com/superdurable/dex/blob/sdk-java/v1.12.0/examples/java/src/main/java/io/superdurable/dex/production/pullworkers/PullGreetingExample.java), [Python](https://github.com/superdurable/dex/blob/sdk-python/v1.12.0/examples/python/dex_examples/production/pull_workers.py), [TypeScript](https://github.com/superdurable/dex/blob/sdk-typescript/v1.12.0/examples/typescript/src/production/pull-workers.ts), or [Rust](https://github.com/superdurable/dex/blob/sdk-rust/v1.12.0/examples/rust/src/production/pull_workers.rs) example at each language's published SDK tag.

Each pull Worker opens outbound streams to its app Worker ID queue and every Flow type it registers. Flow types must be unique within a Dex Server. The app Worker ID identifies one process, changes after every restart, and cannot equal a registered Flow type. Let the SDK generate it unless a deployment needs an explicit process-unique value. Dex first tries the previously used app Worker ID. When that ID has no connected streams after a restart, crash, or deployment, Dex immediately tries the Flow type queue; the sticky wait applies only while that ID still has connected streams. Keep durable state in Dex; sticky routing does not promise the same process.

If no Worker accepts a task within the dispatch wait, a Step gets a retryable unavailable failure that **consumes one Step retry**. An RPC caller gets an Unavailable error. Pull delivery is at least once: a disconnected Worker can receive the same call again if Dex has not received output. Make external effects idempotent and reconcile uncertain outcomes. For a pull target, the local phase of **ASYNC** durability is one attempt; later attempts receive the last recorded heartbeat.

With Server v1.12.0 and a v1.12.0 pull Worker SDK, a Worker that does not register the requested Step type or RPC name declines it before application code runs. Dex excludes that Worker and tries another Worker without consuming a Step attempt. The regular dispatch wait is 10 seconds, including RPCs; the local Step dispatch wait is 3 seconds. If no capable Worker accepts within that wait, the Step receives a named failure and follows its failure and retry policy. The RPC caller receives **FailedPrecondition** naming the RPC, matching the legacy not-registered status code. Older Servers or SDKs retain the prior not-registered Worker error. During a rolling deployment, start Workers that add names before stopping old Workers; keep changed Step logic compatible because old Workers still serve the names they register.

## Startup registration and readiness

Go SDK v1.13.0 adds **Worker.WaitPullRegistered(ctx)**. Launch **Start** in another goroutine and use a bounded startup context to wait until the app Worker ID queue and every registered Flow type queue have each registered at least once. Concurrent waits before or after **Start** are safe. Startup failures wake waiters with their error chain. A cancelled context ends only that wait; it does not stop the Worker. Stop before initial registration and listening mode return errors. Once registration succeeds, later waits return nil, even after Stop; the wait proves registration, not free handler capacity.

Use **Worker.PullRegistrationState().IsReady** for later readiness probes. After initial registration, transient disconnects and ownership moves do not flap readiness. A permanent rejection makes it false only when that queue has no other registered stream. **Queues** exposes **Queue**, **HasRegisteredStream**, and **LastPermanentError** for diagnostics. Successful re-registration clears that queue's error. Stop alone does not clear latched readiness: combine the snapshot with application lifecycle health and remove a stopping Worker from service separately.

Before initial readiness, a permanent rejection on a queue with no other registered stream returns **PullRegistrationError** from the wait. Its **Queue** identifies the rejected queue and **Err** retains the gRPC status. Permanent statuses are **Unauthenticated**, **PermissionDenied**, **InvalidArgument**, **Unimplemented**, and **ResourceExhausted**. By default the Worker keeps retrying rejected streams with a one-minute delay. A rejected surplus stream records **LastPermanentError** and retries while another registered stream keeps the queue ready; matching limits during rolling overlap must not cause a serving Worker to exit.

Go's opt-in **PullWorkerOptions.StopOnPermanentStreamRejection** defaults to false. When true, the first permanent rejection leaving its queue with no registered stream makes **Start** drain all queues within **StopDrainTimeout**, request cancellation after that deadline, wait for handlers, and return **PullRegistrationError**. Handlers must respond to cancellation; the deadline does not force an unresponsive handler to return. Always call **Stop** before process exit; it remains safe after **Start** returns.

For rolling deployments, start replacement Go Workers and wait for their registration before stopping old Workers. Keep handling **Start** failures after startup. Java, Python, TypeScript, and Rust at SDK v1.12.0 do not yet expose these registration readiness APIs or the opt-in rejection shutdown. Rely on Worker process health and watch logs for "Worker task stream rejected"; do not claim that process health proves queue registration. Track parity in [#728](https://github.com/superdurable/dex/issues/728).

## Heartbeats, capacity, and shutdown

Server v1.10.1 enforces the configured **HeartbeatTimeout** for pull Steps, as for listening Workers. Earlier Server v1.10.0 does not enforce it in pull mode. Cancellation reaches a Step handler through heartbeats. A long-running handler that must observe cancellation should record heartbeats within its **HeartbeatTimeout** and handle the resulting cancellation promptly. Set the timeout to tolerate healthy quiet periods while bounding a lost Worker, and keep each attempt within its method timeout.

The maximum concurrent task count caps active handlers. Idle streams per queue keep work ready, and each stream handles one task at a time. For **F** Flow types, size for up to **(1 + F) × (idle streams per queue + maximum concurrent tasks)** streams per Worker. The extra queue is the app Worker ID queue. Keep the result within **matching.maxConcurrentTasksCap** per app Worker ID on each matching owner and plan for **matching.maxStreams** per Matching instance. Busy streams receive no idle Ping, so record task heartbeats often enough to keep load-balancer connections active. See [Server deployment](operations.md#pull-worker-server-setup).

On Stop, the Worker stops accepting assignments and waits for handlers up to its drain timeout (30 seconds by default). It then requests cancellation and waits for handlers to return. A half-closed task stream, including one awaiting a server-directed reconnect, is bounded by the remaining drain deadline. Keep handlers responsive to cancellation and allow shutdown to complete before terminating the process.

For scale to zero, configure [worker.wake](operations.md#worker-wake-hook). Dex sends a best-effort wake notification after the sticky wait and continues the same dispatch attempt. Size dispatch waits, Worker startup time, and Step retry policy together; the notification does not guarantee a Worker starts in time.
