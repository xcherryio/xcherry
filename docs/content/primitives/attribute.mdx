# Attribute

An **Attribute** lets you store data within a Flow execution, as persistence storage.

This is especially useful for intermediate data during a Flow execution. It eliminates the work of setting up and managing a database dependency.

Dex Attribute is not to replace your databases. An obvious limitation is that Attribute exists only for the lifetime of its Flow execution. Dex deletes it when it deletes the Flow execution, after the configurable retention period following Flow closure.

However, Dex allows you to sync Attribute values to your application database as permanent storage. This also lets you build more powerful database indexes to query Attributes.

## Use an Attribute {#define-an-attribute}

Define Attributes as part of the persistence schema of a Flow.

Then you can use the attribute within Step or RPC implementation to read or write the attribute. An attribute must be declared via PersistenceSchema before use. Otherwise, the worker will reject the operations.

When updating an attribute, setting it to null will delete it.

            .indexed(AttributeIndex::keyword().with_key("keyword2"));

                progress: progress.clone(),

            progress,

    fn steps(&self) -> StepList<'_, Self::StartInput> {
        StepList::start(&self.start)

        PersistenceSchema::new()

            .attribute(&self.email)
            .attribute_map(&self.progress)

    progress: AttributeMap<String>,

        self.status.set(context, "completed".to_owned())?;
        Ok(StepDecision::graceful_complete(input))
    }
}

## AttributeMap {#attributemap}

An **AttributeMap** is a family of Attributes with keys decided at runtime. Use one when a Flow needs a changing set of small values, such as the status of each payment or each item in an order.

The reason for **AttributeMap** is to efficiently store a collection of data. Each Attribute is stored as a blob in Dex Server. Putting all data into a single Attribute means every update rewrites the whole blob. AttributeMap lets Dex Server store each instance as an independent blob for higher efficiency.

## Initial Attribute values {#initial-attribute-values}

**StartFlowOptions** can set initial Attributes when the Flow is created. Initial values and Flow creation are one operation, so the first Step sees them immediately. See [Flow options](/primitives/flow/flow-options#attributes).

Applications use Flow RPCs to read and write Attributes after a Flow starts. A Client can also use **WaitForAttributeMatch** to wait until a singleton Attribute or one AttributeMap instance satisfies a scalar comparison. The call returns the matched current value. See [Client](/primitives/client/advanced#wait-for-an-attribute-match).

## Indexed Attributes {#indexed-attributes}

Dex lets you configure indexes for Attributes. With indexing, you can use the field in **SearchFlows** queries to find the Flow executions that match the query.

| Index type | Value |
| --- | --- |
| **KEYWORD** | One exact string. |
| **FULL_TEXT** | Text for tokenized search. |
| **KEYWORD_ARRAY** | A list of exact strings. |
| **INT**, **DOUBLE**, **BOOL** | The corresponding scalar value. |
| **DATETIME** | A date and time value. |

An **index key** is the key in the search schema and the key you use in a query. Index keys consume a finite, namespace-level Search Attribute pool and are shared across Flow types.

The SDK defaults a regular Attribute's index key to its Attribute name. For application indexes, always override that default with an explicit generic numbered key. Keep business names on Attributes and share one typed slot pool across every Flow type in the namespace. Two logical indexed fields in the same Flow need different slots. Reuse a slot across Flow types only with the same index type; its business meaning can differ. Dex system indexes keep their reserved names.

| Index type | Application index keys |
| --- | --- |
| **KEYWORD** | **keyword1**, **keyword2**, … |
| **KEYWORD_ARRAY** | **keywordList1**, **keywordList2**, … |
| **FULL_TEXT** | **text1**, **text2**, … |
| **INT** | **int1**, **int2**, … |
| **BOOL** | **bool1**, **bool2**, … |
| **DOUBLE** | **double1**, **double2**, … |
| **DATETIME** | **datetime1**, **datetime2**, … |

Numbering does not increase namespace capacity. Choose only slots available in the target Temporal visibility store. Renaming an index does not remove its old Search Attribute registration or backfill existing Flow executions. Validate changed example schemas in a fresh local namespace. Plan any existing deployment migration separately.

A generic key can have a different business meaning in each Flow type. Application run queries must constrain **FlowType**. Keep the query unchanged across pages. Dex Web already scopes searches to the selected Flow type. Parenthesize caller filters before combining them with the application scope so an OR cannot bypass it. Do not index sensitive data or PII. The customer-email value in the Customer Refund example is synthetic data only.

An indexed **AttributeMap** must use an explicit index key. It is not an index over all Map instances. Each instance write updates the same search field, so one instance can replace the value written by another instance. The Map instance key is not searchable.

This does not turn the Map into a **KEYWORD_ARRAY**. **KEYWORD_ARRAY** indexes the string array from one write; Dex does not combine the values from all Map instances. After the example below writes the payment instance with value authorized, you can query the current search value with:

```text
FlowType = 'AttributeFlow' AND keyword2 = 'authorized'
```

If another Map instance later writes a different value, that value replaces the search value for **keyword2**. Use a regular Attribute with **KEYWORD_ARRAY** when you need to search a collection of values. Do not use an AttributeMap index to find every instance with a value.

## Locking {#locking}

Concurrent Steps and RPC invocations can read and write the same Attribute. This can lead to race conditions. To avoid this, use Attribute locks. Dex Server ensures only one Step execution or RPC handling can acquire the lock at a time.

### Coordinate writes across the whole AttributeMap {#whole-map-coordination}

An AttributeMap lock protects one exact instance. When an invariant spans several instances or the whole collection, register a separate singleton bool Attribute as its coordination key. For example, register **currentMessages** as an AttributeMap and **currentMessagesLock** as a non-map, non-indexed bool Attribute in the same **PersistenceSchema**.

Every Step, timeout handler, and RPC that writes, deletes, archives, or otherwise changes the protected map must request the same singleton Attribute lock in its method-specific lock options. RPCs declare this fixed lock at registration time. A writer that requests only a map-instance lock does not conflict with the singleton lock. All participating writers serialize within that Flow execution; other Flow executions have their own locks.

The bool value is not the lock state. Do not acquire or release the lock by reading or toggling the value. Dex acquires and releases it around the invocation; the coordination Attribute does not need a persisted value. Locking also does not load map entries. Declare exact instance loads, or a whole-map load when the operation must enumerate instances. RPC lock acquisition can return a lock-conflict error rather than queueing the caller.

Keep per-instance locks for independent partition updates. Use the shared singleton lock when all affected writers must preserve a collection-wide invariant.
