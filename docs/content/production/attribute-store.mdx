# Custom Attribute Store operations

Custom Attribute Store projects selected Flow Attribute writes into PostgreSQL,
MySQL, Databricks, Snowflake, or MongoDB. Dex uses asynchronous, latest-state
writes for one Flow at a time. Delivery is attempted at least once, so every
destination write is idempotent.

Dex never creates, migrates, or backfills a destination. Create the SQL table or
MongoDB collection before starting Dex.

## Configuration

```yaml
attributeStore:
  stores:
    reporting:
      type: postgres
      dsn: postgres://user:password@host/database
      tableName: public.flow_attributes
    operational:
      type: mysql
      dsn: user:password@tcp(host:3306)/database
      tableName: flow_attributes
    orders:
      type: postgres
      dsn: postgres://user:password@host/database
      tableName: public.orders
      rowKey: order-{customer_id}-{order_id}
      columnNaming: snake_case
      attributeMaps:
        LineItems:
          tableName: public.order_line_items
          instanceKeyColumn: line_item_id
    lakehouse:
      type: databricks
      dsn: token:secret@workspace:443/sql/1.0/warehouses/warehouse-id
      tableName: analytics.reporting.flow_attributes
      flowIdColumn: flow_id
    warehouse:
      type: snowflake
      dsn: user:password@account/analytics/reporting
      tableName: analytics.reporting.flow_attributes
      flowIdColumn: flow_id
    documents:
      type: mongodb
      dsn: mongodb://user:password@host:27017
      databaseName: analytics
      collectionName: flow_attributes
  schemaSyncInterval: 1m
  syncBatchSize: 100
  syncAttemptTimeout: 30s
  syncRetryPolicy:
    initialInterval: 100ms
    maximumInterval: 30s
    backoffCoefficient: 2
    maximumAttempts: 0
    totalDuration: 1h
```

Every store requires **type** and **dsn**. Dex never logs DSNs. SQL stores also
require **tableName**. MongoDB instead requires **databaseName** and
**collectionName**; SQL fields and MongoDB fields cannot be mixed.

PostgreSQL and MySQL accept **table** or **schema.table**. Databricks and
Snowflake accept **table**, **schema.table**, or
**catalog-or-database.schema.table**. Missing parts use the connection's current
catalog or database and schema. Identifiers are parsed and quoted. Attribute
values always use driver parameters.

## Startup contracts

Dex connects, pings, and validates every destination during startup. One failure
fails startup and closes already-opened clients.

For PostgreSQL and MySQL without **rowKey**, each table must have exactly one
character-compatible primary key. Dex discovers that key and stores the Flow ID
in it. This preserves the existing configuration and behavior for these stores.
With **rowKey**, the primary key must be exactly the columns the template names,
and each must be a character column.

For Databricks and Snowflake, **flowIdColumn** must name an existing, non-null,
non-generated string column. Values in that column must be logically unique.
Dex does not scan for duplicates, create a constraint, or rely on warehouse
primary-key enforcement. A SQL Warehouse must already be available for a
Databricks connection.

Every other required SQL column must have a default or generated value. This
allows a partial insert to create a row. Attribute names match the remaining
columns exactly, or by their snake_case form under **columnNaming**.

For MongoDB, the configured collection must exist. Dex does not create the
collection, change its validator, or create indexes.

## Row keys and column naming

PostgreSQL and MySQL stores accept two optional settings. Without them, a store
behaves as before. Databricks, Snowflake, and MongoDB reject both settings at
startup.

**rowKey** splits each Flow ID into primary-key columns. Use it when a business
ID is part of the Flow ID and you query by that ID, or when several Flow types
describe one entity. A template contains literal text and placeholders:

- **\{column\}** stores the captured text in that primary-key column.
- **\{*\}** matches text without storing it.
- Each placeholder captures up to the next literal text. The last placeholder
  captures the rest of the Flow ID.
- Literal text must separate two placeholders, and no capture may be empty.

For example, **order-\{customer_id\}-\{order_id\}** splits **order-c1-o-7** into
**customer_id** c1 and **order_id** o-7. A Flow ID that does not match the
template skips its whole batch with an error log, because a retry cannot change
the result. Writes to a key column are filtered like Flow ID writes.

Several stores may name the same table. Each upsert sets only the columns of its
own batch, so two Flow types can write different columns of one row. For
example, a store with **customer-\{customer_id\}** and another with
**onboarding-\{customer_id\}-\{*\}** both write the row of one customer.

**columnNaming: snake_case** writes each Attribute to the snake_case form of its
name. Dex inserts an underscore before an upper-case letter that follows a
lower-case letter or a digit, or that ends an acronym before a lower-case
letter. Then it lower-cases every letter. **DeploymentURL** becomes
**deployment_url**, **URLPath** becomes **url_path**, and **S3Bucket** becomes
**s3_bucket**. When two Attribute names in one batch map to the same column, Dex
filters both. The default writes each Attribute to the column with exactly its
name.

## AttributeMap tables

**attributeMaps** writes each instance of an AttributeMap as one row of its own
table, so SQL can query map instances such as the line items of an order or the
members of a group. Each key is an AttributeMap name:

- **tableName** selects the instance table, as **table** or **schema.table**.
- **instanceKeyColumn** stores the instance key without its escaping: the
  instance written as **LineItems/item%2F7** is stored as item/7.

The instance table's primary key must be exactly the store's primary-key columns
plus **instanceKeyColumn**, all character columns. With
**order-\{customer_id\}-\{order_id\}**, the **LineItems** table needs the primary
key **customer_id**, **order_id**, **line_item_id**. Every other required column
must have a default or generated value. Dex checks the instance tables at startup
and at every schema refresh, like the store's own table.

Writing an instance replaces its row, and deleting the instance deletes the row.
An instance is one complete value, so its row always equals the latest value:

- A JSON object writes each top-level field to the column with the same name,
  under **columnNaming**. A JSON number is written as an integer only where the
  column takes one. Nested objects and arrays go to JSON or JSONB columns.
- Any other value is written to a column named **value**.
- Every other non-key, non-generated column that the value does not set returns
  to its default, or NULL without one.
- A field without a column is skipped. An instance table may store only part of
  each value, so Dex logs a warning once per process for each such field.
- A field that maps to a primary-key column is skipped. Dex logs an error only
  when its value differs from the key.
- A value that does not convert is logged as an error and skipped. The row still
  records the instance.

One batch writes the store row and all its instance rows in one transaction,
with the latest value of each instance. Dex creates no foreign keys between the
tables: a violated constraint would fail the whole batch and hold back the
Flow's later writes until the retry budget runs out. Dex never deletes rows when
a Flow closes.

A Flow that selects several stores writes each AttributeMap only to the stores
that declare it. Other stores treat its instances as ordinary Attributes.
Databricks, Snowflake, and MongoDB reject **attributeMaps** at startup.

## SQL writes and schema refresh

PostgreSQL and MySQL retain their existing upsert statements. With a **rowKey**,
the upsert writes every key column and resolves conflicts on the whole primary
key. Databricks and
Snowflake execute one parameterized **MERGE** for each batch from one Flow. Dex
does not combine batches from different Flows and does not maintain a change
log.

Each SQL store refreshes independently. The one-minute default receives uniform
90–110% jitter every cycle. A successful metadata query atomically replaces the
immutable in-memory schema snapshot. A failed query retains the previous
snapshot and retries after the next interval. MongoDB does not run a schema
refresh loop.

Adding nullable or defaulted SQL columns is discovered without restarting Dex.
A batch that writes a column missing from the current snapshot, in the store's
table or an AttributeMap table, refreshes that store's schema before it writes.
A column that no refresh has found missing refreshes at once; a column that a
refresh already found missing refreshes again at most every 30 seconds. Batches
that arrive meanwhile wait for that refresh. A migration that adds a column
therefore needs no Dex restart, as long as it completes before the Workers that
write the column start.
Removing or changing columns may cause later mutations to be filtered or
retried, depending on whether local validation or SQL execution detects the
change.

### SQL type contract

| Attribute value | PostgreSQL and MySQL | Databricks and Snowflake |
| --- | --- | --- |
| string | Character, varchar, or text; declared length is enforced | String, character, varchar, or text; declared length is enforced |
| int64 | Signed integer or scale-zero numeric; range and precision are enforced | Integer types or scale-zero decimal/number/fixed; range and precision are enforced |
| double | Floating or numeric | Floating types; finite values only |
| bool | PostgreSQL boolean; MySQL boolean, tinyint(1), or bit(1) | Boolean |
| SDK datetime | PostgreSQL timestamp with time zone; MySQL timestamp or datetime | Timestamp types; values are converted to UTC, including timestamps without a time zone |
| JSON object | JSON or JSONB after validation | VARIANT through the destination's native JSON parser |
| other object | PostgreSQL bytea or MySQL binary/varbinary/blob | Binary or varbinary |
| null | Nullable columns only | Nullable columns only |

SDK datetime values may use RFC3339 strings or JSON epoch seconds. Dex rejects
oversized strings or binary values, out-of-range integers, excess decimal
precision, non-finite floating-point values, and invalid JSON.

Missing columns, type mismatches, Flow ID and key column writes, Attribute names
that share one column, and nulls for required columns are logged and filtered
one field at a time. Valid fields in the same batch still
write. If every field is filtered, the sync batch succeeds without executing SQL.

## MongoDB document contract

Each Flow maps to one document. The document **_id** is the Flow ID, and synced
Attributes are top-level fields:

```json
{
  "_id": "customer-42",
  "display_name": "Ada",
  "profile": { "active": true },
  "score": 17
}
```

Dex uses an upsert with a partial field update. Attributes omitted from a batch
remain unchanged. When one batch contains the same Attribute more than once,
the last value wins.

Strings, 64-bit integers, finite doubles, booleans, and null use native BSON
values. JSON recursively becomes BSON documents, arrays, and scalar values;
integers that fit in 64 bits remain integers. Other encoded objects become BSON
binary values.

The Attribute name **_id**, names containing a period or NUL, and names beginning
with a dollar sign are logged and skipped. Other valid fields in the batch still
write. If every field is invalid, the sync batch succeeds without contacting the
collection.

## Delivery and shutdown

Attribute Sync stores latest state, not an event history. A later write may
repeat after an ambiguous failure. SQL upserts, warehouse merges, and MongoDB
upserts therefore use the Flow ID as their idempotency key.

A sync batch first runs a short local phase limited to seven seconds. It uses
the configured backoff intervals and coefficient, but its attempts are bounded
only by that seven-second window. Regular attempts default to 30 seconds and a
one-hour total retry budget. Exhaustion skips that batch. Dex does not
automatically replay old Attributes or backfill a newly configured store.

Filtered writes, missing targets, and retry exhaustion emit error logs.

CancelFlow and FailFlow are cooperative and may wait for active Steps, accepted
locked or transactional RPCs, and multiple one-hour batch budgets. A canceled
Flow closes with Canceled status on every backend. On the Temporal backend, new
locked or transactional RPCs are rejected after terminal finalization begins.
On the Cadence backend, SetAttributes calls and RPC results accepted during
cleanup are drained for their Attribute writes; terminal processing does not
start their next Steps. Terminate and engine timeouts are hard stops and may
leave external storage behind the Flow's state.
