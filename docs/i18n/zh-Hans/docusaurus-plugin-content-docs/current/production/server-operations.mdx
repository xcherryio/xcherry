# 服务器运维

Dex Server 提供 FlowService API、协调持久化 Flow 执行，并提供 Dex Web API。将它作为
具有明确配置、健康检查和访问控制的托管生产服务来运行。

## 本地开发

对于本地 stack，请安装 dexcli 并运行：

~~~bash
brew install superdurable/tap/dexcli
dexcli dev
~~~

这会启动 Dex Server 和 Dex Web 供本地使用。选项请参阅
[CLI README](https://github.com/superdurable/dex/blob/main/cli/README.md)。

## 生产部署形态

- 以带有 readiness 和 liveness check 的托管服务运行 Dex Server。
- 为应用 client 和 Worker 提供稳定、经过认证的 server address。
- 为大 payload 配置持久化 Blob Store。
- 在需要可搜索投影时配置 MySQL 或 PostgreSQL Custom Attribute Store。
- 只通过组织的认证访问路径发布 Dex Web。
- 从每个 Server instance 收集日志和 Prometheus metrics。

独立部署 Server configuration 和应用 Worker 变更。Worker 发布可以改变 Flow 行为；在退役
定义前，使用[应用运维](/production/application-operations#versioning-flow-code)中的
版本控制流程。

## Server 与 SDK 协议兼容性

Dex Server 和每个 SDK release 都声明一个包含上下界的协议区间。两个区间存在交集时，
Worker 才能启动。Worker 先选择交集中的最高协议，再同步 Attribute index，最后绑定
WorkerService。Server 和 SDK 的 artifact version 只用于诊断，不参与兼容判断。

从不支持 **GetServerInfo** 的历史 deployment 升级时，必须先升级 Server。旧 Server 没有
实现该检查，新 Worker 会拒绝连接。首次升级完成后，只要仍保留旧协议，新 SDK 就可以使用
旧 Server；只要区间仍有交集，新 Server 也可以使用旧 SDK。

Server breaking release 会提高最低协议版本。升级此类 Server 前，先停止旧 Worker 及其
流量。在维护窗口内升级 Server 和 SDK，然后恢复流量。也可以使用相互隔离的蓝绿环境，
确保协议区间不相交的 deployment 不会通信。已经运行的 Worker 不会在 Server 升级后自动
重新协商，因此 breaking change 前必须主动停止它们。

协议兼容只覆盖 Worker 与 Server 之间的 API。它不能替代开放 Flow 的兼容策略，包括
Flow type name、Step graph 和持久化 payload。

## Server 组件

dex-server 镜像默认在同一个 process 中启动 Dex Web、API、Interpreter 和 Matching。容器在 8801
端口提供 FlowService，在 8802 端口提供 Dex Web。是否发布任一端口仍由 deployment
显式决定。

使用 **services** 启动选项运行任意非空组件组合。当组件需要不同的 replica 数量或
resource limit 时，将它们分开部署：

~~~bash
dex-server start --services web
dex-server start --services api
dex-server start --services interpreter
dex-server start --services matching
dex-server start --services web,api
~~~

仅部署 Interpreter 且没有 **internal.listen** 时，必须将
**interpreter.interpreterActivityConfig.internalServiceTarget** 设置为 API service。
配置私有 listener 时，Interpreter 默认使用本地地址。
仅部署 Web 时不会连接 Temporal 或 Cadence。Web 会在 API upstream 可用前启动，因此
**/healthz** 只报告 Web process 的健康状态。在 FlowService 可用前，Web API request
会返回 upstream error。

## Pull Worker 路由

**matching** 角色拥有 pull Worker 队列。API 实例接收 **PollWorkerTask** stream，
并将每条 stream 转发到队列 owner。Interpreter 和 API 实例即使不拥有队列，也会加入
membership。至少运行一个 Matching 实例。共享 membership cluster 的所有实例必须
使用同一个 backend namespace 和 membership seeds。

单进程可省略 **membership**，使用本地单成员 ring。多实例部署需要在每个 Server
process 上配置 **membership** 和私有 **internal** listener：

~~~yaml
membership:
  listen: 0.0.0.0:6833
  broadcastAddress: ""
  refreshInterval: 10s
  seeds:
    dnsName: dex-headless.dex.svc.cluster.local:6833
internal:
  listen: 0.0.0.0:8803
  tokenFile: /etc/dex/internal-token
matching:
  dispatchWait: 10s
  stickyWait: 5s
  localDispatchWait: 3s
  localStickyWait: 2s
  localExecutionReserve: 4s
  maxConcurrentTasksCap: 256
  maxStreams: 100000
  maxQueueLength: 256
  maxFlowTypes: 256
  maxFlowTypeLength: 256
  pingInterval: 20s
~~~

**membership.listen** 绑定仅供副本访问的 ring listener，默认值为 **0.0.0.0:6833**。
**broadcastAddress** 默认取第一个私有 IPv4 地址，并与绑定端口一起对外发布。
**seeds.dnsName** 解析 headless service；也可以使用 **seeds.static** 指定 peer
地址列表。私有 gRPC listener 绑定 **internal.listen**。绑定 host 为 wildcard 时，
Dex 使用 membership broadcast host 和 internal port 作为发布地址。使用固定的
internal port，并确保 peer 可以访问该地址。
**refreshInterval** 默认是 10 秒。

API 角色默认使用 8801 端口。客户端和 pull Worker 通过该端口访问 API 实例。
仅运行 Matching 或 Interpreter 的实例不开放 8801 端口。公开负载均衡器只能选择
API 实例。在 Kubernetes 中，使用 NetworkPolicy 将 internal listener 和 6833
端口限制为仅供 Dex 副本访问。membership cluster 必须配置 **internal.tokenFile**。
internal listener 使用明文 gRPC，应加密其网络路径。**MatchingService** 只在私有
listener 上提供。未配置 membership 或 **internal.listen** 时，Dex 为其绑定本地
loopback 端口。关闭 **auth** 时，公开 listener 仍提供 **InternalService**，以兼容
现有 Interpreter 连接。配置 **internal.listen** 和 **internal.tokenFile** 可通过
私有 listener 访问该服务。仅运行 Interpreter 的进程只会在配置 **membership** 时
加入 membership。

**matching.maxStreams** 限制每个 Matching 实例上的已注册 stream 数。
**maxConcurrentTasksCap** 限制该 owner 上单个 **appWorkerID** 的 stream 数。
**maxQueueLength** 限制队列名长度，**maxFlowTypes** 和 **maxFlowTypeLength**
限制每个 Worker 的注册内容。等待预算默认使用上述值。Dex 每隔 **pingInterval** 向空闲 poll stream
发送 **Ping** frame。负载均衡器必须支持长时间运行的 HTTP/2 stream，且 idle timeout
大于该间隔。忙碌的 stream 不会收到这些 Ping；Worker 应足够频繁地发送任务心跳
frame，以保持负载均衡器连接活跃。公开 endpoint 必须保留双向 streaming。

## 配置

Server 配置是 YAML 和有类型的 Go 配置。生产配置不同于 **dexcli dev** 接受的有限 flag。
将配置保存在已批准的 secret-management 和部署系统中，而不是应用镜像中。

Blob Store section 名为 **blobStore**。其中的 entry 使用 **BlobStoreConfigEntry**。
旧的 **externalStorage** key 不被接受。

在 **web** section 中配置 Web listener 和 API upstream：

~~~yaml
web:
  bindAddress: 0.0.0.0
  port: 8802
  flowServiceTarget: dex-api:8801
  flowRenderingDirectory: ""
  startFlowWorkerTargetHeadless: false
~~~

bind address 默认监听所有 interface，port 默认是 8802。空的
**flowServiceTarget** 使用 localhost 和已配置的 API port。Web connection 使用
plaintext gRPC，并复用 **api.grpcMaxMessageBytes**，因此应将其限制在可信
network path 内。

**web.startFlowWorkerTargetHeadless** 控制所有从 Dex Web 启动的 Flow 的 Worker routing。默认值为 false，启动后不可变。对应的环境变量是 **DEX_WEB_START_FLOW_WORKER_TARGET_HEADLESS**。只有操作员填写 Kubernetes headless Service address 时才启用它。

## 身份认证

公开 API 默认不启用身份认证。配置 **auth.authenticators** 后，所有公开的 unary
调用和 stream 都必须携带 bearer credential；健康检查仍然开放。Dex 按配置顺序尝试
authenticator。静态 token 文件保存 SHA-256 哈希。JWT authenticator 使用缓存的
JSON Web Key Set 校验签名、issuer、audience 和有效期。

~~~yaml
auth:
  authenticators:
    - kind: staticTokens
      file: /etc/dex/public-tokens.yaml
    - kind: jwt
      issuer: https://issuer.example
      audiences: [dex]
      jwksURL: https://issuer.example/keys
      caFile: /etc/dex/issuer-ca.pem
internal:
  listen: 127.0.0.1:8803
  tokenFile: /etc/dex/internal-token
~~~

静态 token 文件保存 SHA-256 哈希：

~~~text
tokens:
  - sha256: HASH
~~~

使用至少具有 128 bit 熵的 token，文件中只保存其哈希。Dex 会重新加载发生变化的 token 文件。
JWT 配置省略 **jwksURL** 时，Dex 通过 issuer 的 OpenID 配置发现 key set。
**caFile** 为 issuer 的 HTTPS endpoint 添加 PEM 证书包，系统根证书仍然有效。

启用 **auth** 后，**InternalService** 和 **MatchingService** 只在 **internal.listen** 上运行，并要求
**internal.tokenFile** 中的 token。Interpreter 发送文件第一行的 token；listener
接受每一行，便于轮换。每个 token 至少需要 32 个字符。该 listener 使用明文 gRPC。应绑定到 loopback，或限制网络
访问并加密流量。单独部署的 Interpreter 必须将
**interpreter.interpreterActivityConfig.internalServiceTarget** 指向此 listener。
关闭 **auth** 且未配置独立 internal listener 时，这两个 service 使用公开 API listener。

目前启用 **auth** 后只有 Go SDK 能连接。Dex Web、CLI，以及 Java、Python、
TypeScript 和 Rust SDK 还不能提供所需 credential。

可选的 Worker wake hook 配置在 **worker.wake** 下：

~~~yaml
worker:
  wake:
    url: https://operator.example/worker-wake
    budget: 120s
~~~

Worker 不可用时，Dex 向 hook 发送包含 **target** 和 **kind: wake** 的 POST。
推送模式下，Dex 在同一次尝试中最多等待 **budget**，默认 120 秒。拉取模式下，
**target** 是 Flow 类型队列。黏性等待结束后，Dex 发送唤醒通知，并在同一次
dispatch 尝试中继续等待。成功 dispatch 后发送 **kind: active**。
通知尽力发送，并按 target 限速。配置 **internal.tokenFile** 时，Dex 将内部 token
作为 bearer credential 发送；否则不发送 authorization header。

## 连接受保护的 Temporal 集群

在 **interpreter.temporal** 下配置 Temporal frontend 连接。API key 需要轮换时，将其挂载为文件：

~~~yaml
interpreter:
  temporal:
    hostPort: temporal-frontend:7233
    namespace: my-namespace
    apiKeyFile: /var/run/secrets/dex/temporal-token
    apiKeyFileRefreshInterval: 30s
    tls:
      enabled: true
      caFile: /etc/dex/temporal-ca.pem
      serverName: temporal-frontend.example
      certFile: /etc/dex/tls/tls.crt
      keyFile: /etc/dex/tls/tls.key
~~~

Dex 启动时读取 **apiKeyFile**。文件不存在或内容为空时，启动失败。Dex 最多每隔 **apiKeyFileRefreshInterval** 检查一次文件变化；默认间隔为 30 秒。刷新期间，请求继续使用最近一次有效的 key。后续读取失败或文件变空时，Dex 记录警告并保留该 key。静态 key 使用 **cloudAPIKey**，轮换 key 使用 **apiKeyFile**，两者不能同时配置。Temporal Cloud Operations 可使用任意一种 key 来源。

配置 key 时，TLS 默认使用系统 CA。没有 key 或其他 TLS 设置时，默认使用明文连接。即使省略 **tls.enabled**，设置 **tls.caFile**、**tls.serverName**、**tls.certFile** 或 **tls.keyFile** 也会启用 TLS。将 **tls.enabled** 设置为 true，可以在没有其他 TLS 设置时启用 TLS。**tls.caFile** 中的证书会替代系统 CA；**tls.serverName** 覆盖服务器证书校验使用的名称。Dex 仅在启动时加载 CA，轮换 CA 后必须重启 Dex。同时设置 **tls.certFile** 和 **tls.keyFile** 可启用双向 TLS。Dex 启动时加载证书和私钥，并在新的 TLS 握手时重新加载发生变化的文件。

同时配置 API key 和 **tls.enabled: false** 会以明文发送凭据。Dex 会记录警告。仅在允许明文凭据的网络路径上使用此配置。**tls.enabled: false** 不能与其他 TLS 设置同时配置。

## Blob Store

在允许超过 inline limit 的 payload 前配置持久化 store。为每个环境使用独立凭据和
least-privilege policy。监控 write 和 read failure，并测试 credential rotation 后仍能读取
现有 object 的恢复流程。

Dex 默认将不超过 100 bytes 的持久化 payload 保留在 history 中。101 bytes 的 string 或 encoded
object 会被 offload。可通过 **blobStore.thresholdInBytes** 覆盖默认值。
比较时只计算 payload size，不计算最终 reference size。

当 RPC option 或 server 配置要求事务执行时，只读 handler 也会按事务执行。handler 是否
写入状态，与 RPC 是否使用事务，是两个独立的选择。

是否 offload 到 Blob Store，取决于这个 value 是否需要持久化。非事务 RPC 将输入直接发送给
Worker，将输出直接返回给调用者。Dex 不会持久化这些输入和输出。事务 RPC 的输入和输出
需要持久化，使用 Blob Store threshold。

任何 RPC 返回的状态变更，例如 Attribute 写入、Channel 消息和后续 Step 输入，都需要
持久化，使用相同的 threshold。非事务只读 RPC 不会写入 Blob object，也不会将 RPC 调用记入
Flow history。加载已有状态时，可能需要读取已有的 Blob object。

完整 Worker 请求超过 **api.grpcMaxMessageBytes** 时，Dex 会在调用 Worker 前拒绝该请求。

**api.grpcMaxMessageBytes** 控制 Dex server 各 listener 以及 server 调用 Worker 时的上限，
默认值为 32 MiB。一条消息包含一个或多个应用值，以及已加载状态、批量条目和 metadata 等
外层开销。应让该上限比最大的应用值高出明确的余量。默认值为不超过 16 MiB 的值保留 16 MiB 余量。

每个 SDK 使用自己的上限，增大 server 上限不会提高 SDK 的上限。Go SDK 的 Client 和 Worker
默认接收上限为 32 MiB，可通过 **GrpcMaxMessageBytes** 修改。其他 SDK Worker 的 gRPC 接收上限
默认为 4 MiB。包含已加载状态和 metadata 的完整 Worker 请求必须同时满足这两个上限。超过任一上限时，都会返回 **FailedPrecondition**，
其中 **SubStatus** 为 **WORKER_API_ERROR**，**OriginalWorkerErrorStatus** 为
**ResourceExhausted**（8）。事务和非事务 RPC 使用相同错误。事务请求被 Dex 的大小检查
拒绝时，不会重试。

~~~yaml
blobStore:
  thresholdInBytes: 100
  objectIdLength: 10
  asyncStepInputSnapshotsEnabled: true
  supportedStorages:
    - status: active
      storageId: p1
      storageType: s3
~~~

由于每个 offloaded value 都会把 **storageId** 写入 durable history，请保持该值简短。例如，
在含义仍清楚时，用 **p1** 代替 **production1**。

应用必须将 Blob reference 视为 opaque value。其 wire format 为：

~~~text
String: <storageId>|<base36DayOffset>/<objectId>
Object: <storageId>|<base36DayOffset>/<objectId>

示例：p1|c/ab3de7kp2x
~~~

Value arm 用于区分 String 和 Object reference。Object Blob 保存完整的 **EncodedObject**，
其中包括 **json**、**raw** 或 custom encoding。reference 保留 storage ID 和 UTC write date，
但不保存 Flow ID 和 encoding。Dex 从可信的 request 或 Worker context 获取 owner Flow ID。
物理 object path 为：

~~~text
<namespace>/<YYMMDD>$<escapedFlowId>/<objectId>

示例：default/260913$coding-session--c08256c4/ab3de7kp2x
~~~

reference date 是从 2026 年 9 月 1 日 UTC 起算的全小写 Base36 日序，并且没有前导零。
**0** 表示 2026 年 9 月 1 日，**c** 表示 2026 年 9 月 13 日，**10** 表示 2026 年
10 月 7 日。物理路径继续使用 **YYMMDD**，其中两位年份表示 2000 到 2099 年。

常见 Flow ID 字符会在物理路径中保持可读。Dex 只对 object-key path segment 中不安全的
字符进行 percent escaping。例如，**SubFlow:parent-step-0** 会变成
**SubFlow%3Aparent-step-0**。input snapshot path 中的 Run ID 和 Step execution ID 继续使用
Base64URL encoding。

internal reference 只属于一个 Flow。在 reference 跨越 Flow boundary 前，Dex 会先 hydrate，
再为目标 Flow 重写。目标 Flow 会收到 inline value，或收到存储在自身 Flow prefix 下的新
object。因此，删除源 Flow 不会损坏目标 Flow。public API 会拒绝客户端提交的 internal
reference。

object ID 使用确定性的全小写 Base36 字符。同一个 invocation ID 和 stored bytes 的 retry 会
覆盖同一个 object，不会生成重复 object。Object stored bytes 包含 encoding。Dex 不执行
read-before-write、conditional create 或 collision retry。**blobStore.objectIdLength** 默认值为
10。0 表示使用默认值，负数无效，正数没有协议规定的范围。写入同一个
Blob Store namespace 的所有 Server 必须使用相同值，而且 Server 运行期间不能修改该值。
reader 接受任意非空的全小写 Base36 ID，因此 deployment 可在协调重启时修改配置长度。

10 位 Base36 提供约 51.7 bits。在单个 Flow 的单个 UTC day partition 内，10,000 个 object
至少发生一次碰撞的近似概率为 1.4 × 10⁻⁸；100,000 个时为 1.4 × 10⁻⁶；1,000,000 个时为
1.4 × 10⁻⁴。普通 deployment 使用 10。高吞吐 Flow 使用 12 或 16。长度 50 可以表达完整
SHA-256 值。更长的值只会增加前导零，不会增加 entropy。

cleanup 保留每个 Flow prefix 开头的 UTC date。它按字典序分页列出 prefix，解码转义后的
Flow 和可选 Run，并且只在 execution 已不存在时删除整个 prefix。随后使用返回的
continuation token 继续 list；该过程不使用 manifest。

ASYNC Step input snapshot 在 Blob Store 启用时默认开启。它会保留成功的 ASYNC local
Step method 收到的准确 input，供 semantic history 展示。snapshot 不受 payload offload
threshold 影响，也不是 Flow execution、retry 或 recovery 所必需。将
**blobStore.asyncStepInputSnapshotsEnabled** 设置为 false 可跳过这项可选的 history
成本。关闭后，ASYNC local completion event 会将 input 标记为 unavailable。SYNC method
和 fallback 到 regular Activity 的 ASYNC method 仍会从 backend history 获得 input。

可选的 **blobStore.blobCache** 缓存 S3 支持的 Attribute object。非空 **directory** 会启用
它，并且只能属于一个 Server process。默认 budget 为 1 GiB。过大或被拒绝的 object 会
绕过 cache，继续访问源 Blob Store。损坏的 entry 会被失效并重新填充；初始化、恢复和
disk I/O error 是 Server error。local Blob Store object 和 Step-event input snapshot 不使用
此 cache。

## Stream Store

配置 **streamStore** 后可启用 best-effort [Stream](/primitives/stream)。单个本地 Server
process 可以使用 memory backend。多个 Server process 需要共享 retained messages 时，
请使用 Redis 7 或更高版本。Redis backend 需要 **redisURL**。将 Redis 配置为
**noeviction**，使 capacity pressure 表现为可见的 Stream write failure。

**maxMessageBytes** 控制每条 serialized message 的大小，默认值为 100 KiB。
**maxReadMessages** 控制每个倒序分页的上限，默认值为 1000，并且必须为正数。Stream
capacity 仍由各个已注册的 Stream definition 提供。其余 Stream Store 设置用于控制
approximate charging、trim watermark、trim batch、lease 和 worker concurrency。

## 应用 Search Attribute 槽位

复用通用槽位的应用搜索必须限定 **FlowType**，并将调用方条件放在括号内。翻页时保持查询不变。

## Custom Attribute Store

当关系型 projection 支持运维搜索或业务报表时，使用 Custom Attribute Store。请遵循
[自定义 Attribute Store](/production/attribute-store)中的 schema 和 retry 要求。将其
数据库、凭据、migration 和 backup 作为 Dex deployment 的生产依赖。

## Dex Web 访问控制

Dex Web 可以显示 Flow input、output、Attribute 和 Worker stack trace。将它放在 TLS 以及
强制认证的 reverse proxy 或 gateway 后。按 role 授权生产访问，并将其限制给需要检查
Flow data 的 operator。

不要将 Dex Web 或 FlowService API 直接公开到公网上。使用 network policy、认证传输和
权限最小化的 service identity 保护 Server 和 Worker endpoint。按照你的 data-handling
policy 审计对生产 Flow detail 的访问。
