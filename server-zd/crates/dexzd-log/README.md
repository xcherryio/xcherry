# dexzd-log

## Purpose

Command log batch format and the conditional-write commit protocol that makes server-zd writes durable in object storage.

The codec stores a protobuf header, one zstd frame per partition, and an xxh3-128 trailer. Partition reads use two object-store range requests and verify the frame checksum. Full reads verify the trailer and every frame.

`recover_stream` scans forward from the last applied sequence and effective epoch. An empty store uses `recover_stream_from` with the manifest segment's first sequence and epoch zero. Recovery writes EpochStart at the first gap. It then lists the stream beyond it, voids every older pipelined object there, and fills each other gap below the last object with another EpochStart of the new epoch, so the log stays dense and replay reads it seq by seq. The pipeline starts after the last listed object. An object of the new or a newer epoch in that range fences recovery. An older write that lands after the listing still stops the node, and the next start recovers again. Log cleanup deletes only batches below a published snapshot's applied position, so a pipelined gap always follows an existing batch. If the first batch to read and the batch before it are both missing while a later batch exists, cleanup deleted batches the caller still needs. Recovery then returns `LogError::MissingBatches` and writes nothing. The engine records the effective epoch with its applied position so recovery can resume after older log objects are removed. The returned batches are in apply order. `CommitPipeline` accepts opaque record bytes, writes batches with `CreateOnly`, and emits committed batches in sequence order. The engine applies those batches before answering application requests.

`StreamRecovery` runs the same recovery one step at a time, so callers apply each accepted batch as it is read instead of holding the stream in memory; `recover_stream` and `recover_stream_from` collect those steps. The steps return each accepted batch in seq order up to the first missing seq; a batch older than the epoch of an earlier EpochStart is void and not returned. `StreamRecovery` reports only the number of voided batches, so its memory does not grow with the log; the collecting functions also list the voided seqs. `OrderedBatchReader` reads consecutive batches with up to `LogReadAheadConfig::max_read_ahead_batches` GETs in flight and returns results, including errors, strictly in seq order. It lists the stream one page of 1,000 keys at a time and requests the next page once fewer than a page of listed seqs, or a window if larger, remain unread, so LIST latency stays hidden. It reserves each batch's listed object size before its GET. A read starts only while the reservations fit in `max_buffered_bytes`. A reservation covers a read in flight, a fetched batch, and the batch last returned until the caller asks for the next one, so it is released as batches are applied and a large batch stops limiting reads once it leaves. A failed read, decode, or stream identity check releases that batch's reservation when `next_batch` returns its error, and further reads start in the freed bytes at once. Cancelling `next_batch` leaves reads in flight and their reservations with the reader, which resumes them on the next call; dropping the reader releases them. Fetched batches stay as object bytes and are decoded when they are returned, so the budget bounds the memory read-ahead holds even for well-compressed batches. A batch larger than the budget, or a seq the listing did not show, is read alone. The object bytes held therefore never exceed the larger of the budget and the largest batch, whatever the length of the log. A batch whose bytes differ from its listed size fails with `LogError::Corrupt` at its seq. Recovery stops at the first missing seq in that order and discards later reads unseen, so the gap rule, voiding after an EpochStart, and hole filling match a one-GET-at-a-time scan. Hole filling reads ahead only up to the last listed batch.
